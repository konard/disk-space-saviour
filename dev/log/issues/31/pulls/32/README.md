## Root causes and solutions

### Errors

**E1. Release Preflight: `npm refused the OIDC package exchange (404)` (run 37987850798, attempt 1).**
This is the preflight added in PR 30 doing its job: it calls npm's OIDC package exchange, the endpoint `npm publish` uses, before anything is versioned. The npm trusted publisher still named `konard/disk-space-saviour` (see `dev/log/issues/29/pulls/30`), so the exchange was refused and the release stopped with an explicit message instead of failing at publish time. Fixing it takes a setting on npmjs.com, not a code change. A maintainer made it, and the re-run at 22:00 printed `PASS: npm OIDC package exchange verified (returned token discarded)` and published `0.15.1` (`ci-logs/run-37987850798-attempt2-*.log`). No code change is needed.

**E2. "Check for Changesets" and "Dry-run release versioning (PR only)" fail on this branch with `No unreleased changesets found` (run 38000089291).**
The release of `0.15.1` consumed the previous changeset, so this branch had none. Fixed by `.changeset/ci-issue-31.md`. Both checks are working as intended.

**E4. Deno, all three OSes: `install-git-hooks` "fails when husky leaves core.hooksPath unset" and "reports it when husky says nothing" (`Expected 0 to be 1`), and `pr-guards` "requires an explicit opt-in to directory scanning locally" (`Expected 1 to be 0`).**
The fixtures delete `CI` from a copy of `process.env` and run the script with `spawnSync`. Node gives the child exactly that `env`. Deno's `spawnSync` and `execFileSync` pass `clearEnv: false` and merge it into the parent's environment, so on a runner the child still saw `CI=true` and took its CI branch. The fix for denoland/deno#27343 cleared the env only for async `spawn`. Locally the tests passed because `CI` was unset. `CI=true GITHUB_ACTIONS=true deno test -A` reproduces all three failures; `experiments/deno-spawn-env-deleted-var.mjs` shows the leak directly. `9490eec` blanks the variables instead of deleting them (`tests/helpers/env.js`); the scripts treat blank as unset. The same change applies to the two `detect-code-changes` push-range tests, which deleted keys from an override object and so could never unset a variable that the runner set. `prependPath` now filters instead of deleting. `tests/env.test.js` fails on any env deletion in a test file (4 files before the fix). Reported as [denoland/deno#36996](https://github.com/denoland/deno/issues/36996).

**E5. Deno on Windows: seven `git-safety` and `issue-27-details` tests fail with `PermissionDenied: Access is denied. (os error 5): utime '...\.git\objects\61\03f3...'`.**
`age()` in `tests/helpers/fixtures.js` dates a fixture repository, including Git's read-only objects. Deno sets file times through `filetime::set_file_times`, which on Windows opens the file with `GENERIC_WRITE`, and Windows refuses that on a read-only file. libuv opens the file with only `FILE_WRITE_ATTRIBUTES` (`src/win/fs.c`, `fs__utime_impl_from_path`), so Node and Bun succeed. `c7fd55b` retries a failed call on a file without the write bit after granting it, then restores the mode. Reported as [denoland/deno#36997](https://github.com/denoland/deno/issues/36997).

**E6. Bun, all three OSes: `check-package-manager.mjs` "passes on this repository" fails on `::warning::lockfile(s) for another package manager at the repository root: bun.lock`.**
The test asserted that no warning was printed at all. CI's Bun leg runs `bun install` first, which writes `bun.lock`, and that warning is correct. `bbc8988` asserts only what W2 changed: no warning names `deno.lock`.

**E7. Windows, Node, Bun and Deno: "Deno CI leg grants the permissions the fixtures need" fails.**
The regex required `parallel\n`, but Windows checkouts end lines with `\r\n`. `bbc8988` accepts `\r?\n`.

**E8. Docker-in-Docker Integration on `8f41657` (run [37995633245](https://github.com/link-foundation/disk-space-saviour/actions/runs/37995633245)): `docker pull -q docker:28-dind@sha256:2a23… failed (1): … auth.docker.io/token …: context deadline exceeded`.**
A Docker Hub outage, not a code defect: the next run passed. `tests/integration/dind.mjs` pulled each pinned image once, though `.github/actions/setup-buildx-resilient` already handles this kind of outage for the buildx image (issue 75). `tests/integration/pull-pinned.mjs` brings the same policy here: three attempts with a 5s, then 10s delay, then the same digest from `mirror.gcr.io`. Both digests are on the mirror (checked with `docker manifest inspect`). `experiments/dind-pull-mirror-fallback.mjs` runs the fallback against a real daemon with Docker Hub failing; `tests/pull-pinned.test.js` covers the retry order and requires a digest.

**E9. Deno on Windows: changeset-config "versions and formats the real package with Deno absent from PATH" fails with `spawnSync node ETIMEDOUT` (runs [38005973122](https://github.com/link-foundation/disk-space-saviour/actions/runs/38005973122), [38006829682](https://github.com/link-foundation/disk-space-saviour/actions/runs/38006829682) and [38007233544](https://github.com/link-foundation/disk-space-saviour/actions/runs/38007233544)).**
The test copies the package into a temporary directory and runs `changeset version` there with a 20s `spawnSync` timeout. Changesets 3 formats what it writes through `@changesets/format`, which runs `npx prettier --write` with tinyexec. On Windows that is five processes: `cmd.exe`, `npm-prefix.js`, `npx-cli.js`, `cmd.exe` and `prettier.cjs`. The first `deno test -A --parallel` of a windows-2025 job spent 17–21s on this step in seven runs, and every run that reached 20s failed. The same file run again in the same job took 1.4–2.2s, and the Windows Node and Bun legs run the whole test in 3–8.5s. The run on `bbc8988` passed, so the 20s limit was crossed only some of the time. The `EBUSY` in 38007233544 has the same cause: the timeout killed `node`, its children still held files in the directory, and `rmSync` failed.

`DSS_DEBUG=1` preloads `tests/helpers/report-lifetime.cjs` into every Node process of the fixture through `NODE_OPTIONS`. Each process logs when it started, what it spawned, when its children exited and when it exited. A temporary CI step repeated the cold run with the trace (run [38009230580](https://github.com/link-foundation/disk-space-saviour/actions/runs/38009230580), `ci-logs/run-38005973122-38009230580-windows-deno-changeset.log`). It took 17107ms:

| Phase                                                                           | ms   |
| ------------------------------------------------------------------------------- | ---- |
| `spawnSync` until changesets starts                                             | 759  |
| changesets loads and reads the changeset, up to its first `git log`             | 4352 |
| `git log`, then `cmd.exe` and `npm-prefix.js` (357ms) until `npx-cli.js` starts | 543  |
| `npx-cli.js` until it starts prettier                                           | 4463 |
| prettier `--write` (476ms) until `npx-cli.js` exits                             | 579  |
| the outer `cmd.exe` exits and changesets sees it                                | 5540 |
| changesets exits and Deno's `spawnSync` returns                                 | 871  |

At +12746ms the changesets process was still waiting on its `cmd.exe` child (`ProcessWrap` and its pipes), five seconds after `npx-cli.js` had exited. `cmd.exe` is not a Node process, so the trace cannot show what it did in that time. The warm runs go through the same chain in 2s, and every phase above is a process that starts and runs normally. So this is the first-run cost of the runner, not a hang. `6fdbbfb` keeps `spawnSync` and raises the timeout to 60s. Node and Bun still stop each test at 30s (`--test-timeout=30000`, `--timeout 30000`), and the Deno step keeps its 200s budget.

The first attempt, `425b44b`, waited for the child's exit event, not for its pipes to close, on the theory below. The fixture passed in 19s, but the helper's own proof test failed on Windows. Node puts non-detached children in a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so the grandchild that was meant to hold the pipe died with its parent (80ms against the expected 3000ms). The traces then showed that the child was running the whole time, so `6fdbbfb` removes the helper.

**Side finding, not the cause of E9 and not filed: Windows handle inheritance in Deno and libuv.**
On Windows a child inherits every inheritable handle of its parent, not only its own stdio. If one thread makes a child's pipe ends inheritable and another thread starts a process at that moment, that process also holds the pipe, and a `spawnSync` on the first thread sees EOF only when it exits. [The Old New Thing](https://devblogs.microsoft.com/oldnewthing/20111216-00/?p=8873) describes the race and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, the way to limit what a child inherits. Deno 2.9.7 calls `CreateProcessW(..., TRUE /* Inherit handles */, ...)` without a lock (`runtime/subprocess_windows/src/process.rs`), and so does libuv (`src/win/process.c`). Rust std holds `CREATE_PROCESS_LOCK` around the call, citing Microsoft KB315939 (`library/std/src/sys/process/windows.rs`). `experiments/windows-pipe-inheritance.mjs` keeps 16 three-second sleepers running on a worker thread while the main thread times 150 quick `spawnSync` calls (`ci-logs/run-38007233544-pipe-inheritance.log`). Deno on windows-2025 had 3 calls of about 3048ms. Node with worker threads on Windows, and both runtimes on macOS and Linux, had none. It is not filed because it did not cause E9, there is one 150-call sample, and the same unlocked pattern is in libuv. The experiment stays in the repository for a report that needs it.

**E3. Broken Link Checker fails on this branch (run 38000089234): 5 errors in `upstream/hive-mind-CI-CD-BEST-PRACTICES.md`.**
The copied document links to its siblings (`CI-CD-BEST-PRACTICES.zh.md`, `CONTRIBUTING.md`, …), which exist only upstream. lychee checks `md,html`, so the snapshot is now stored as `.txt`, the same way issue 29 stored its template snapshots.

### Hazards found while fixing F1

- `deno test --parallel` runs files in workers that share one working directory, so no test may call `process.chdir`. The commit-message test passes `cwd` instead.
- `deno test` with `nodeModulesDir: "auto"` rewrites `node_modules` (it installed prettier 3.9.9 over the npm tree) and can touch `deno.lock`. CI legs are separate jobs, so only local runs need `git checkout deno.lock && npm ci --ignore-scripts` afterwards (`docs/CONTRIBUTING.md`).
- A fixture started from a shell is outside Deno's node-compat argument translation, so it must run through `deno run -A` (without it the first `process.env` read fails). The CommonJS gh fixture was renamed from `fake-gh.js` to `fake-gh.cjs` for the same run (`tests/create-github-release.test.js`, commit `6560ed6`).
- Sequential `deno test -A` took about 152s locally; `--parallel` took 40–50s (49s in the last full run). The budget is 200s.
- A bare `bun test` collects every file named like a test anywhere in the tree, while Node runs `tests/*.test.js` and Deno `tests/`. An experiment named `*.test.mjs` made Bun report 1111 tests with 2 skips against Node's 1108. It is now `experiments/test-anywhere-describe-skip.repro.mjs`, and `tests/visible-skips.test.js` fails if a test-named file appears outside `tests/`.

## Best-practice checklist (hive-mind CI-CD-BEST-PRACTICES)

- **No silent success:** a test that cannot run is reported as skipped with its reason, never as passed or absent (F1). A guard test keeps new gates out.
- **Same coverage on every runtime:** Deno runs the fixtures with `-A`, so the three runtimes differ only by the skips each summary lists.
- **Tools see their real configuration:** jscpd fails a test on unknown keys (F4); zizmor runs online in both passes (F2).
- **Triggers cover every input a job reads** (F3).
- **Warnings are actionable or gone:** W1–W3 are fixed. Every other warning is listed above with the reason it stays.
- **Fail closed before release:** the preflight stopped the release on E1 with the cause, before anything was versioned.
- **Bounded jobs:** the Deno step has a 200s budget with a warning at 70%, like every other step (`docs/CI-TIMEOUT-BUDGETS.md`).
